# 企业化改造：设计与实施计划

> 实施细节、代码位置与逐步操作手册见 **`CONCURRENCY_GUIDE.md`**；
> 本文只保留分期与验收目标的概览。


依据 2026-11-15 的并发实测（并发 5 → QPS 6.0；并发 20 → QPS 5.9、p50 3.6 秒）
与六项根因，按「先测量、再改架构、最后上部署」分四期。每期都有可复测的验收指标。

## 现状基线（修复前）

| 场景 | 并发 | QPS | p50 |
|---|---|---|---|
| 列表 | 5 / 20 | 6.0 / 5.9 | 820 ms / 3 368 ms |
| 检索 | 5 / 20 | 5.6 / 5.5 | 892 ms / 3 579 ms |

吞吐与并发无关（约 6 QPS），说明瓶颈是服务端串行，不是网络或客户端。

## 六项根因

1. 单进程单 worker（`uvicorn workers=1`）
2. 全局 `LOCK` 串行化读路径
3. SQLite 单写 + 每文档一次索引状态查询
4. Qdrant 本地模式（单进程 + 目录锁）
5. 本地 Embedding 串行（`LocalQwen` 内部锁，一次一条）
6. 索引单线程（`ThreadPoolExecutor(max_workers=1)`）

## 第一期：把读路径的串行去掉（不换存储）

| 动作 | 预期 | 验收 |
|---|---|---|
| 索引状态批量读取：一次查询取全部 `index_runs`，列表不再逐份查 | 列表 120 ms → <40 ms | 列表 QPS ≥ 20，p50 < 200 ms |
| 列表不再持有全局锁做序列化构造，只在取数据时持锁 | 读并发不再互相排队 | 并发 20 时 p50 < 500 ms |
| 搜索查询向量缓存（同问题 60 秒内复用） | 重复提问不再重复编码 | 同问题并发 20，p50 < 300 ms |

不改存储、不改协议，风险最低，先拿收益。


## 第一期结果（2026-11-15 实施后复测）

同一台机器、同一批 123 份文档、同一脚本 `scripts/load_probe.py`：

| 场景 | 修复前 | 修复后 | 变化 |
|---|---|---|---|
| 列表 5 并发 | 6.0 QPS / p50 820 ms | **55.7 QPS / p50 86 ms** | QPS ×9.3，延迟 ÷9.5 |
| 列表 20 并发 | 5.9 QPS / p50 3 368 ms | **55.6 QPS / p50 350 ms** | QPS ×9.4，延迟 ÷9.6 |
| 检索 5 并发 | 5.6 QPS / p50 892 ms | 6.1 QPS / p50 813 ms | 基本持平 |
| 检索 20 并发 | 5.5 QPS / p50 3 579 ms | 6.1 QPS / p50 3 250 ms | 基本持平 |

做了什么：

1. 索引状态批量读取 —— 列表不再逐份查 `index_runs`（一次查询取全表，
   严格校验仍留在详情接口）
2. 列表先切片再构造记录 —— 一页 10 条不再为全库付索引查询的成本
3. 查询向量缓存（同问题 300 秒内复用）—— 已实现，**但检索吞吐没有变化**

### 检索为什么没变

缓存命中后省掉的是 Qwen 编码，但检索的大头不在这里：每次检索仍然要
`candidates()` 遍历全部文档、重建快照（`snapshot` + `chunks` 读库），
并且这一段在全局锁内。**瓶颈是候选集重建，不是编码。**

这条要放到第二期：把「文档 → 有效快照」做成内存缓存并在文档变更时失效，
才能让检索真正并发起来。

## 第二期：状态外置（为多 worker 铺路）

| 动作 | 原因 |
|---|---|
| 会话/草稿/票据从进程内存搬到 SQLite（带 TTL） | 现在 `sessions/drafts/tickets` 在进程内，多 worker 会互相看不到 |
| `MANAGED_RAG` 按会话改为无状态构造 | 同上 |
| 索引状态查询改为单条 SQL JOIN | 去掉逐份 snapshot |

验收：两个 uvicorn worker 同时服务，登录后任意 worker 都能续上会话。

## 第三期：把重活移出请求进程

| 动作 | 原因 |
|---|---|
| 解析/切分/索引走独立 worker 进程 + 任务表 | 现在靠线程池 + 子进程，重启即丢 |
| Embedding 独立服务（可换 GPU 或批量） | CPU 串行是检索吞吐的硬顶 |
| 去掉 180 秒单文档上限，改按任务类型配置 | 大 PDF 与 Docling 冲突 |

验收：并发上传 50 份不互相阻塞；服务重启后任务可续。

## 第四期：换存储与部署

| 动作 | 原因 |
|---|---|
| SQLite → PostgreSQL | 单写瓶颈，且要支持多 worker |
| Qdrant 本地 → 独立服务 | 本地模式不能多进程/多机 |
| HTTPS + 反向代理 + 只读副本 | 现在只绑 127.0.0.1，别的机器连不上 |
| 备份与恢复脚本 | 业务库、向量、原件三处要一致 |

验收：`ab -n 1000 -c 50` 下 QPS ≥ 100、p95 < 1 s；断网演练可恢复。

## 原则

- 每一期都先补测量脚本，再改代码，改完用同一脚本对比
- 任何一期不通过验收就不进入下一期
- 期间保持「单机演示版」可用，不破坏现有 422 项测试与 18 项业务流

## 第二期进展与实测归因（2026-11-15）

做了：候选集缓存（`IndexService._candidate_map`，2 秒 TTL）。检索 6.1 → **6.7 QPS**，
p50 3 250 → 2 951 ms —— **提升有限**。

归因（离线测量，128 份文档、约 300 个 chunk）：

| 环节 | 耗时 |
|---|---|
| `all_docs()` 全表反序列化 | 2 ms |
| 逐份读 `chunk_runs` + `chunks` | 2 ms |
| BM25 over 300 chunks | 4 ms |

都不是瓶颈。**真正的上限是「单进程 Python + GIL」**：一次检索约 150 ms 的纯 CPU
（BM25 分词、记录构造、结果后处理）只能在一个核上排队。

结论：想把检索从 6 QPS 提到 20+，靠改代码里的缓存没用，必须**多进程**；
而多进程卡在两件事上：

1. **Qdrant 本地模式**（`QdrantClient(path=...)`）目录锁，不能被多个进程共享
2. **会话/草稿/票据在进程内存**，多 worker 之间看不到

这两条分别属于第四期（Qdrant 独立服务）和第二期（状态外置），**必须一起做**，
单做任何一半都不会有吞吐收益。

## 第三、四期的前置条件（本轮未执行）

| 项 | 需要什么 | 不做的后果 |
|---|---|---|
| Qdrant 独立服务 | 起容器 + 改 `QdrantClient(url=...)`，索引需重建 | 无法多 worker |
| 状态外置 | 会话/草稿/票据写 SQLite，带 TTL | 多 worker 会话错乱 |
| PostgreSQL | 替换全部 `sqlite3` 调用与 SQL 方言 | 写入仍是单写 |
| HTTPS + 反代 | 证书、域名、监听地址调整 | 只能本机访问 |
| 备份恢复 | 库 + 向量 + 原件三处一致性脚本 | 出事无法恢复 |

这些都会改变演示机的部署形态（需要常驻容器与证书），不是「改代码即完成」。
按当前决策（单机演示），建议停在第一期成果，二期以后另立项目推进。

## 第三、四期的实施结论（2026-11-15 尝试后）

已完成的铺垫：

| 项 | 状态 |
|---|---|
| Qdrant 独立服务 | ✅ 容器 `p18-qdrant` 起在 `127.0.0.1:6333` |
| `P18_QDRANT_URL` 开关 | ✅ 有值走服务端，无值走本地目录 |
| SQLite WAL + busy_timeout | ✅ 多进程可共享读 |
| `P18_WORKERS` 开关 | ⚠️ 只能为 1，>1 会明确报错并指向本文件 |

**为什么不能直接开多 worker**：uvicorn 的 `workers>1` 要求应用是导入字符串，
而当前应用是运行时组装的 `DatasetsApp`；更关键的是，RAG 的会话、草稿、票据都在
**进程内存**（`RagService.sessions/drafts/tickets/receipts`），第二个 worker 看不到，
会让用户拿到的票据在下一个请求里变成 `ticket_expired`。

所以 2/3/4 期真正的前置顺序是：

1. **状态外置**：把上述四个 dict 换成 SQLite 表（带 TTL），值用写通代理保证
   `session['at']=...` 这类嵌套赋值能落库
2. **应用工厂化**：把 `experience_server.py` 的模块级逻辑收进 `build_app()`，
   供 `uvicorn.run("...:build_app", factory=True, workers=N)` 使用
3. 然后再谈 PostgreSQL、HTTPS、备份

第 1、2 步是纯代码改造，但会动 RAG 的核心路径，需要一整轮完整回归（422 测试 +
18 项业务流 + UI），不适合夹在演示环境里做一半。

本轮**没有**把 `P18_WORKERS` 留成可用但错误的开关——超过 1 会直接失败并提示，
避免有人打开它以后遇到随机的 `ticket_expired`。
